# Subagent 派工指南：怎麼讓 Claude Code 把事情分給小幫手做

給醫學背景、不寫程式的朋友。你不需要懂軟體工程，只要把 subagent 想成**「你請的住院醫師 / 研究助理」**：你是主治，負責判斷與決策；翻病歷、跑大量資料、查文獻這種耗時的活，交給助理做，只聽他報告結論。

---

## 1. 為什麼要派工？

Claude Code 的主對話有一個「工作記憶」（context）。你讓它一次讀 20 個檔案、搜尋一堆網頁，這些原文全部堆在主對話裡，會有三個後果：

- 越塞越滿，後面越來越慢、越貴、越容易忘記前面的指示。
- 主對話被一堆中間過程淹沒，真正重要的決定反而被稀釋。
- 一次出錯，整段對話都被污染。

派 subagent 的好處：它在**獨立的空白對話**裡做完事，只把**結論**交回來。主對話保持乾淨。

## 2. 什麼時候派、什麼時候自己做

| 情境 | 做法 |
|---|---|
| 要讀超過 **3 個檔案**，或超過 **500 行** 才能回答 | 派出去 |
| 掃整個資料夾（找出所有用到 X 的地方、盤點結構） | 派出去 |
| 查網頁、查文獻、讀長篇外部文件 | 派出去 |
| 同一個修改要套用到 3 個以上檔案 | 派出去 |
| 讀很大的 log / 資料檔 | 派出去 |
| 單一事實查詢（知道檔案在哪、查一個值） | **自己做**，派人反而更貴 |
| 改一行、改錯字 | 自己做 |
| 回答你的問題、做決策 | 自己做 |
| 已經派出去的事 | **不要自己再做一遍**，等報告 |

一句話判準：**「這件事的中間過程（檔案全文、搜尋結果、網頁內容）需要留在主對話嗎？」不需要 → 派出去。**

> 為什麼單一查詢不派？每開一個 subagent 都要付「開機成本」（見第 7 節），小事派人比自己做更貴。

## 3. 派工三件套（缺一不可）

給 subagent 的指令（prompt）一定要包含：

1. **目標與動機**：要做什麼，以及為什麼。動機很重要，遇到邊界情況時它才知道怎麼取捨。
2. **驗收條件**：可以客觀檢查的清單，例如「檔案 X 存在且包含章節 Y」「測試全部通過」。不要寫「做好一點」。
3. **回報格式**：回什麼、多長、什麼格式。

**重要觀念**：subagent **看不到你和 Claude 之前的對話**。派出前自問：「把這段指令拿給一個完全沒看過我們對話的人，他做得出來嗎？」做不出來，就是資訊給不夠。

### 回報的規矩（寫進每個派工指令）

- 只回：**結論 + 檔案位置 + 決定性證據**（例如測試輸出摘要、關鍵數字）。
- **長的產物（報告、大量搜尋結果）寫成檔案，只回傳檔案路徑**，不要整篇貼回主對話。
- 正常回報控制在 500 字內。
- **失敗要照實說**：試了什麼、卡在哪、缺什麼。不接受「大致完成」。完成 = 驗收條件全部通過，否則就是沒完成。
- 同一件事探索 3 次還沒結果 → 停手，回報缺什麼，不要一直繞路硬試。

## 4. 不要自己驗收自己：找一個全新的檢查員

寫的人腦中帶著「我覺得我寫對了」的偏見，這和臨床上「開刀的人不應該自己做 M&M 評核」是同一個道理。

- **多步驟、委派出去、或高風險**的任務：交付前派一個**全新對話**的 agent 驗收。
  - 檔案 / 設定檔：重新讀一次，逐條對照驗收條件，回報 PASS / FAIL。
  - 程式 / 分析腳本：真的跑一次（用範例資料），看輸出，不是「看起來沒問題」。
  - 高風險（要寫進論文的數字、大量刪除或改動、要對外公開的內容）：再加第二意見，例如另一個模型獨立檢查。
- **給驗收員的內容**：驗收條件 + 檔案路徑。**不要**告訴它你是怎麼做的，免得污染它的判斷。
- 小事（改錯字、一行修正）不用另開驗收員，直接看執行結果或讀回即可。

## 5. 升級階梯：什麼時候換更強的模型

| 模型 | 角色 | 比喻 |
|---|---|---|
| **Haiku** | 最快最便宜，做機械、可被檢查的工作 | 實習生 / 工讀生 |
| **Sonnet** | 預設主力：照清楚的規格實作、研究彙整、讀回驗收 | 住院醫師 |
| **Opus** | 最強：架構設計、原因不明的疑難問題、對關鍵產出的對抗式審查 | 主治醫師 |

**升級規則**

- Haiku 做錯一次 → 直接升 Sonnet 重派，不要讓 Haiku 再試。
- Sonnet 同一個子任務連錯兩次 → 升 Opus，而且要**附上完整失敗紀錄**（兩次各試了什麼、錯誤訊息原文、已排除的假設）。沒有失敗紀錄的升級等於浪費。
- **同一個做法最多重試 2 輪**。第 3 輪之前必須改變一件事：換模型、換做法，或補充新資訊。
- 貴的模型解出做法之後，剩下同型的工作**降級**給便宜模型批次套用（附上一個做好的範例）。

**原則：寧可規格寫清楚 + 便宜模型，不要規格模糊 + 貴模型。** 如果規格寫不清楚，代表你自己還沒想清楚，先想，或先派人收集事實。

## 6. Haiku 該擔任什麼角色？一個判準就夠

> **「Haiku 做錯了，能不能被便宜地抓到？」**

- **能** → 交給 Haiku。例如：有測試可以跑、做完可以讀回比對、有標準答案可以對照、或本來就是「要量不要準」的工作（格式轉換、批次改名、初步分類、找檔案、列候選文獻清單、整理排版）。
- **不能** → 交給 Sonnet / Opus。例如：會寫進論文的結論、會影響臨床判斷的內容、需要跨多個檔案理解架構的修改、「通過就自動對外公開」的檢查關卡（漏判不會被便宜抓到）。

兩個常見的小陷阱：

- 從全文抽數字時，Haiku 和 Sonnet 都會把「只有文字描述、沒有數字」（例如「無明顯出血」）誤填成 0。規格要寫明：**沒有數字 → 填 NA，不可填 0**，且每個數字要附原文句子。
- 讀文獻的批次工作，**一隻 agent 一次讀 3–5 篇**，不要一篇派一隻（每隻都有固定開銷）。

## 7. 優先用「輕量 agent」：實測的開機成本

每個 subagent 一啟動就要先載入自己的工具與規則，這是**固定開銷**。以下是 2026-10-20 在作者自己環境的實測（每個 agent 剛啟動、還沒開始工作時的 token 用量；數字依你的 MCP 設定而異，看量級即可）：

| Agent | 開機 tokens | 用途 |
|---|---|---|
| general-purpose（預設萬用） | 約 71k | 什麼都能做，但最貴 |
| `lite-auditor` | 約 16k | 唯讀稽核：讀回檢查、diff、比對檔案 |
| `web-researcher` | 約 18k | 網路調研、fact-check、確認網址 |
| `lit-extractor` | 約 18k | 從 PubMed / PMC 抽數字（需先裝 PubMed MCP，選用） |
| `browser-qa` | 約 24k | 網頁視覺 / RWD / console 錯誤檢查（只診斷） |

這四個 agent 已經放在本 plugin 的 `agents/` 資料夾，安裝後即可使用。**它們功能刻意收窄**（不能改檔、不載入你的 CLAUDE.md），所以：

- 純機械的讀回 / 比對 → `lite-auditor`（錯了容易抓到，還可以加 `model: haiku` 更省）。
- 查資料 → `web-researcher`；抽文獻數字 → `lit-extractor`；看網頁 → `browser-qa`。
- 需要套用你自己的規則（統計解讀、要進論文的文字、臨床內容）、需要登入、需要改既有檔案 → 用 general-purpose。

## 8. 平行優先：獨立的事同時派

如果有 **2 個以上互相獨立的子任務**（不依賴彼此的結果、不會改到同一批檔案），**在同一則訊息裡一起派**，不要一個做完再做下一個。有依賴關係才串行。

- 兩個 agent 會改同一個專案資料夾 → 改成串行，或請它們各自在獨立的 worktree 裡做（避免互相覆蓋）。
- 長任務可以放背景執行，完成時會自動通知，不用一直問進度。
- 要不要合併成一隻，看品質不看數量：多個子任務**共用同一批資料**，或**結果需要互相對照**才看得出問題 → 合併給一隻；彼此獨立、資料不重疊 → 分開派。
- 要處理 5 個以上同流程的項目（例如 10 章稿件逐章處理）→ 不要開一個 session 依序做 10 項（對話越拉越長、越來越貴），改成「一項一個新對話」。

> 費用提醒：同時派很多隻 agent 會同時消耗額度。大規模（例如超過 6 隻平行、或預估跑超過 30 分鐘）建議先讓 Claude 報告規模再動工。

## 9. 可直接複製的派工模板

把【】換成你的內容。每份都已內含三件套。

### 模板 A：搜尋 / 盤點（適合 Explore 或 Haiku）

```
在【資料夾路徑】搜尋【要找什麼】。

目標與動機：我需要【答案的用途，例：確認哪些檔案用了這個欄位，才能安全改名】。
範圍：只搜【路徑 / 檔案類型】；不要讀【排除項，例：備份資料夾、原始資料】。
搜尋提示：可能的命名有【關鍵字、別名、拼法變體】。

驗收條件：
- 每個結果附 檔案名稱:行號
- 說明你搜過哪些關鍵字、哪些資料夾，讓我判斷有沒有漏
- 找不到也是合法答案，但要列出你試過的關鍵字

回報格式：結果清單（檔案:行號 + 一行說明），400 字以內，不要貼大段原文。
```

### 模板 B：實作（Sonnet；規格模糊時先別派）

```
在【專案路徑】實作【功能一句話】。

目標與動機：【為什麼要做；我原本想解決什麼問題】
規格：
- 輸入：【】　輸出：【】
- 邊界情況（至少 2 個）：【例：空白輸入、重複的值】
- 風格參考【既有檔案 X】；只能動【允許的檔案清單】，其他一律不碰
- 不要加沒被要求的功能

驗收條件：
- 【測試或執行指令】通過，既有功能沒壞
- 用【範例資料】實際跑過一次，輸出符合預期
- 每一處改動都能對應到上面規格的某一條

回報格式：改了哪些檔案 + 執行輸出最後 10 行 + 你做過的取捨。500 字以內。
若卡住：說明試了什麼、卡在哪、缺什麼，立刻回報，不要硬繞。
```

### 模板 C：研究 / 查證（Sonnet；醫學問題優先用文獻資料庫而非一般搜尋）

```
研究問題：【一句話，可回答的形式】

目標與動機：【答案會拿去做什麼決定，這決定研究要多深】
來源優先序：【例：官方文件 > 原始論文 > 部落格】
時效要求：【例：只要 2024 年以後的資訊，註明版本】

驗收條件：
- 每個關鍵結論附來源（網址 / PMID）與發布日期
- 區分「來源明說的」與「你推論的」，推論要標出來
- 來源互相矛盾時並列呈現，不要自行挑一個
- 查不到也是合法答案，列出你查過哪裡

回報格式：結論先行（最多 5 條）→ 每條的證據與來源 → 完整筆記寫到【檔案路徑】，只回傳路徑。
```

### 模板 D：審查 / 驗收（全新的檢查員；用 lite-auditor 或 Opus）

```
審查【檔案路徑 / 修改範圍】。

目標與動機：這是【什麼東西】，將用於【用途】。你是第一次看到它的獨立審查者，
請獨立判斷，不要假設它是對的。

驗收條件（逐條回 PASS / FAIL / 無法判定，並附證據）：
1.【條件一，可客觀檢查】
2.【條件二】

另外請主動找：
- 互相矛盾的規則或數字
- 提到的檔案、指令、欄位名稱是否真的存在（用指令驗證，不要用猜的）
- 容易被誤讀的模糊語句

回報格式：PASS / FAIL 表 + 問題清單（位置 + 一句話 + 建議修法），依嚴重度排序。
沒問題就回「沒問題」，不要為了顯得有貢獻而硬找小問題。
```

## 怎麼用：把這段貼進你的 `~/.claude/CLAUDE.md`

`~/.claude/CLAUDE.md` 是 Claude Code 每次開對話都會讀的「個人守則」。檔案不存在就新建一個。把下面整段貼進去（約 20 行）：

```markdown
## 派工守則（Subagent）
1. 預估要讀 >3 個檔或 >500 行、掃整個資料夾、查網頁/文獻、批次改 3 個以上檔 → 派 subagent，主對話只收結論與檔案位置。單一事實查詢、改一行 → 自己做，不要為它開 agent。
2. 派工 prompt 必含三件套：目標與動機 / 可客觀檢查的驗收條件 / 回報格式。subagent 看不到對話歷史，必要資訊都要寫進 prompt。
3. 長產物寫成檔案、只回傳路徑；正常回報 ≤500 字；失敗要照實回報（試了什麼、卡在哪），不可說「大致完成」。
4. 驗收不自驗：多步驟、委派型或高風險任務，交付前用全新對話的 agent 驗收（檔案讀回、程式實跑）；驗收員只拿驗收條件與路徑，不拿做法。小事用執行輸出自證即可。
5. 升級：Haiku 錯一次直接升 Sonnet；Sonnet 同一子任務連錯兩次 → 升 Opus 並附完整失敗紀錄；同一做法最多重試 2 輪，第 3 輪前必須換模型、做法或補資訊。
6. Haiku 判準：「它做錯了能不能被便宜抓到？」能（有測試/可讀回/有標準答案/只要量不要準）→ Haiku；不能（進論文、影響臨床判斷、跨檔架構、自動對外公開的檢查）→ Sonnet / Opus。
7. 輕量 agent 優先：讀回/比對 → lite-auditor；網路調研/fact-check → web-researcher；PubMed 抽數字（需 PubMed MCP）→ lit-extractor；免登入網頁 QA → browser-qa。需套用你自己 CLAUDE.md 規則、要改檔、要登入 → general-purpose。
8. 有 ≥2 個彼此獨立的子任務（不依賴彼此、不改同一批檔）→ 在同一則訊息平行派；會改同一專案就串行或各用獨立 worktree。
9. 讀文獻類工作一隻 agent 批次處理 3–5 篇，不要一篇一隻。從全文抽數字時：只有文字描述沒有數字 → 填 NA，不可填 0，且每個數字附原文句子。
```

貼好後，重開一個 Claude Code 對話就會生效。想確認，直接問 Claude：「你的派工守則是什麼？」

## 選用的進階玩法（沒有也完全不影響上面的方法）

- 高風險產出（要投稿的數字）可以再找另一個 AI（例如 OpenAI Codex）獨立檢查一次，當作第二意見。
- 如果你的專案用規格驅動的開發流程（例如 OpenSpec），平行派工請走該流程提供的指令，不要另外散派。
